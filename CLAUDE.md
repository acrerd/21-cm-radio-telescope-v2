# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project context

This is a complete control system for a Small Radio Telescope (SRT) at Acre Road Observatory, replacing the legacy software in `../acreroad_1420-master`. The original product spec is in `../claude.md` (the parent folder). The legacy hardware spec is in `../acreroad_1420-master/docs/MOTOR_CONTROL_HARDWARE_SPEC.md`.

## Build / run commands

PlatformIO is invoked via the conda-installed binary at `~/.platformio/penv/Scripts/pio.exe` (Windows). All builds should be done from this absolute path — `pio` is not on PATH.

**Arduino Due drive firmware** (this folder):
```
~/.platformio/penv/Scripts/pio.exe run -e due           # build
~/.platformio/penv/Scripts/pio.exe run -e due -t upload # flash
~/.platformio/penv/Scripts/pio.exe run -e simulation    # build host-side simulation
```

**ESP32 controller firmware** (`esp32_controller_arduino/`):
```
cd esp32_controller_arduino
~/.platformio/penv/Scripts/pio.exe run                  # builds wt32-eth01 (default)
~/.platformio/penv/Scripts/pio.exe run -e wt32-eth01 -t upload
~/.platformio/penv/Scripts/pio.exe test -e native       # host unit tests
```
The deployed board is the **WT32-ETH01** and it is the default build. The `esp32s3` environment is legacy (that board is no longer used) — keep it compiling when convenient but WT32-ETH01 is the canonical target and must always build clean.

The `native` environment runs `test/test_coordinates` and `test/test_pointing` on the host — the pure computation, no board attached. It builds only `coordinates.cpp` and `pointing.cpp` (`build_src_filter`); `test/shim/` supplies the little of `Arduino.h`/`Preferences.h` that `pointing.cpp` touches, so the firmware source is compiled exactly as it is flashed rather than copied into the test. On the observatory Linux host use `~/.platformio/penv/bin/pio test -e native`.

**Receiver scheduler** (`receiver_scheduler/`):
```
cmd //c "c:\Users\graha\Desktop\new_SRT\new_SRT_drive\receiver_scheduler\run_scheduler.bat"
```
Always launch via the absolute path to the .bat — relative paths fail. The bat activates radioconda then runs `python h1_web_scheduler.py`. Web UI on `http://localhost:5000`.
On the observatory Linux host, the scheduler re-execs under `/home/astro/radioconda/bin/python` when available. The controller web UI and OTA target are `http://192.168.50.120/`.

**Controller network** (issue #10, done 2026-08-19; full build procedure in `docs/OBSERVATORY_HOST_SETUP.md`): the controller is *not* on the observatory LAN. It sits on a private point-to-point link — a TP-Link TG-3468 (`enp5s0`, `r8169`) in the observatory computer, NetworkManager connection `srt-link`, `ipv4.method shared`, host at `192.168.50.1/24`. Shared mode supplies the address, the DHCP/DNS server and the NAT together; the last matters because the controller syncs from `pool.ntp.org` and time errors become pointing errors through GMST — a link with no route out mispoints overnight. The controller stays on **DHCP**: its address is pinned by MAC in `/etc/NetworkManager/dnsmasq-shared.d/srt.conf` (`dhcp-host=70:4B:CA:58:59:8B,192.168.50.120`), so nothing on the controller is configured for this link and the whole change reverses by moving one cable back to the campus switch. Second fallback is the WiFi AP at `192.168.4.1`, which is up regardless of Ethernet settings. Access from other machines on the observatory LAN is deliberately not set up. When verifying NAT, a **fresh sync after a reboot** is the real proof: `sync_count` reset to 1 with a small `last_sync_age_s`. `"source":"NTP"` alone proves nothing about the *network*, because `NTP_SERVER_FALLBACK` is a numeric address — the clock syncs whether or not DNS works, and did so all through the period when the controller could not resolve a name at all. (This is not the #9 caveat, which was about a stale clock being reported as synced and is fixed: success is now only ever declared by `onTimeSync()`.)

## Architecture

Four loosely-coupled subsystems talking over serial / HTTP:

```
Stellarium ──TCP:10001──┐                       Scheduler (Flask) ──┐
                        ↓                                            ↓
              ESP32 controller (web UI :80 at 192.168.50.120, web_server.cpp) ─────────┘
                        ↓
              UART (Serial1, 115200, line-oriented ASCII)
                        ↓
              Arduino Due drive firmware (src/main.cpp)
                        ↓
              Motors / encoders / limit switches
```

**Drive firmware** (`src/main.cpp`, single file ~1900 lines): bare-metal motor control on Arduino Due. Position is tracked in **pulses** (`PULSES_PER_DEGREE = 2`) by ISRs on FALLING edges of reed-switch encoders. Direction is inferred from the static DIR pin at the time of the pulse. Motor sense for both axes is inverted in software via `AZ_DIR_INVERT` / `ALT_DIR_INVERT` macros in `include/config.h` — every read/write of `PIN_DIR_AZ`/`PIN_DIR_ALT` must go through `AZ_DIR()` / `ALT_DIR()`.

**Coordinate model**: position 0 (in pulses) corresponds to the hardware lower limit (`azHwMin = 0°`, `altHwMin = 0°`). Displayed degrees = `position / PULSES_PER_DEGREE`. After homing, both axes read (0, 0). The `getHomeAzOffsetPulses()` / `getHomeAltOffsetPulses()` helpers compute home as `cfg.homeAz/Alt * PULSES_PER_DEGREE` directly — they do **not** subtract `azMin`. Any new code that touches the relationship between pulse counts and degrees must respect this.

**Homing** (`performHoming()`): three-phase. (1) `driveToLimits()` ramps up to full speed and runs into the hard stop until pulses stop for `stallTimeoutMs`. (2) `backOffFromLimits(5°)` reverses with the same ramp. (3) `driveToLimits()` again, slower, to set the precise zero. Both helpers use `calculatePWM(INT32_MAX, startTime)` to get the standard ramp-up profile without ever entering the ramp-down branch. After Phase 3 both `positionAz` and `positionAlt` are zeroed.

**Motion controller** (`updateAxisMotion`): runs from the main loop only when not in `STATE_HOMING`/`STATE_FAULT`. The IDLE→DRIVING transition only fires if a `newTargetAz`/`newTargetAlt` flag was set by a command — this prevents the controller from chasing stray encoder pulses into a limit switch when idle. `executeDrive()` is the only place that sets these flags.

**Stall detection** requires *both* `(now - driveStartTime) > stallTimeoutMs` *and* `(now - lastPulse) > stallTimeoutMs`, so a stale `lastPulse` from a long idle period can't trigger a false stall the moment a new slew starts. When a stall happens while driving negative within 2° of the hardware limit, it's treated as "arrived at limit" — position snaps to the limit and `targetAz/Alt` are clamped, no fault.

**Encoder ISR debouncing**: `lastPulseAz/Alt` is **only** updated on pulses that pass the debounce window. Updating on every edge (the original bug) caused total pulse loss when motor speed approached the debounce window — every edge reset the timer and nothing ever counted. Don't reintroduce that.

**Current sensing**: `checkCurrentLimits()` always uses the **filtered** current (`filteredCurrentAz/Alt`), never the raw reading. The zero-current sensor offset is **continuously re-tracked** while each axis is `MOTION_IDLE` (in `updateFilteredCurrents()`), so long-term hall-effect drift settles toward zero on its own.

**Driver fault flags**: H-bridge fault outputs (`FF1`/`FF2`) are noisy at motor stop/start due to inductive kickback and supply sag. `checkFaultFlags()` requires the same fault to persist for `FAULT_FLAG_PERSIST_COUNT` (5) consecutive calls before reporting it.

**Status output dedup**: `outputStatus()` builds a `statusCompare` string excluding the live current readings, then prints to the programming-port `Serial` only when that string differs from the last printed one. The full `statusLine` (with currents) always goes to `Serial1` (controller) so the ESP32 sees every update. STATUS commands received over Serial1 (`cmdFromSerial1 == true`) respond only to Serial1 and never touch the programming-port dedup buffer.

**Configuration**: `Config cfg` lives in RAM and is persisted to flash via DueFlashStorage. All defaults are `#define`s in `include/config.h`. `loadDefaults()` must initialize every field of `cfg` — missing any field causes garbage values until `SAVE` is called. Add new tunable parameters by: (1) adding a `#define DEFAULT_X`, (2) adding a field to the `Config` struct, (3) initializing it in `loadDefaults`, (4) handling it in `processSetCommand`, (5) printing it in `showConfig` and `showHelp`.

**Simulation environment** (`-e simulation`): overrides `analogWrite`/`digitalWrite`/`analogRead`/`attachInterrupt` via macros so the firmware runs without real hardware. `simulatePulses()` is called from the main loop and inside the homing while-loops to advance position based on commanded PWM. When you change the homing flow or any in-loop motor control, it must still work in simulation — both `due` and `simulation` environments must build cleanly.

**Galactic plane target**: `getGalacticPlaneTrackingTarget()` walks outwards along b = 0 from the galactic centre and returns the first longitude at or above `settings.galacticMinAlt` (45° default), preferring the higher of the two equidistant candidates. That floor is an **acquisition** threshold, not a horizon — the target is followed down afterwards until `settings.horizonAlt` parks the dish. It is high on purpose: the galactic centre is at Dec −28.9° and culminates at 5.2° from Glasgow, so it never clears the 10° horizon (0 hours in a year) and the old "Galactic Bulge" button was permanently in fallback. At 45° a point exists ~73% of the time and never within ~45° of longitude of the centre. Endpoint is `/track/galactic-plane`, target name `"Galactic Plane"`, `/ephemeris` key `plane`.

**Pointing frames** (`esp32_controller_arduino/src/pointing.{h,cpp}`): two coordinate frames meet at the ESP32 and the boundary is that file. **True alt/az** is where the dish looks on the sky, computed with the *true* site lat/lon; **drive** is what the mount mechanically is, encoder pulses quantised to 0.5°, and the Due works only in drive coordinates. `trueToDrive()` converts one way (applying refraction, then the model terms), `driveToTrue()` inverts it by fixed point on `trueToDrive()` itself so the two cannot drift apart. Every goto, track and manual move goes through `trueToDrive()` before `SRTSerial::sendDriveTarget()`; every *measured* position — `/status` RA/Dec and galactic l/b, Stellarium — goes through `driveToTrue()` first. Arrival and slew-completion checks stay wholly inside the drive frame.

Consequences that must not be undone: the **observing horizon** (`settings.horizonAlt`) is a true-frame test applied *before* the transform, while the **mount limits** (`mountAltMin/Max`, `mountAzMin/Max`) are drive-frame and clamp *after* it — these were once merged into a single `effectiveTrackingHorizonAlt(mountAltMin)`, which is why neither was testable alone. The operator's `/offset` boxes are a deliberate sky-frame displacement layered on top of the calibration, never a replacement for it. **Refraction is applied whether or not a model is loaded** (it is physics, not calibration), so `sun_scan.refraction_deg()` must stay identical to `refractionDeg()` in `pointing.cpp` and the fit must subtract it, or it gets counted twice.

The ESP32 `settings.stowAlt/stowAz` is the position the dish **parks** at, and it is the one exception to the rule above: it is held in **drive** coordinates and the pointing model is deliberately bypassed on the stow path (`main.cpp` park-on-set, `/go-home`). Parking is mechanical — "leave the mount here" — not an observation. The default is zenith facing south (90, 180), and at the zenith the distinction is not academic: azimuth is degenerate there and the model's `tan(alt)` azimuth term asks for a ~50° correction that moves the beam by exactly nothing, so through the model it would park at drive azimuth 170. It is still clamped to the mount limits, and `state.targetAlt/targetAz` are deliberately *not* written by `/go-home` because those hold a true-frame target.

`settings.stowAlt/stowAz` is unrelated to the Due's `cfg.homeAlt/homeAz`, which are also drive coordinates but mean the *encoder origin* — what the limit-switch stall corresponds to. Both were once called "home"; do not merge them again.

**Pointing model wire format**: the scheduler fits it (`sun_scan.fit_pointing_model`), builds the document with `pointing_model_document()`, and POSTs it to `/pointing/apply`; the controller stores it in its own NVS namespace (so a settings reset cannot discard it) and `/pointing/clear` erases it. The document carries the fitted terms (`IE`, `IA`, `AN`, `AE`, and optionally `CA`, `NPAE`, `TF`) and nothing derived from them. Unknown term names are ignored so a richer model can be pushed to older firmware; a missing `version` or a malformed number rejects the whole document rather than applying half of it. This replaced pushing the model as a fictitious `observer_lat`/`observer_lon` plus a write to the operator's offset boxes — the observer position is now the true site position and `/apply` no longer touches it.

Scan records carry `record_version` (`sun_scan._SCAN_RECORD_VERSION`). Version 2 records hold an absolute (T, D) datum — the Sun's true position and the **reported drive position** the mount reached — so every fit is absolute and no delta composition is needed. Version 1 records are residuals against a model that is no longer knowable and are skipped by the fit. Because D is now measured rather than guessed at, the old `_MOUNT_QUANTISATION_SIGMA_DEG` floor is gone.

**ESP32 controller** (`esp32_controller_arduino/src/`): Arduino-framework PlatformIO project, two target boards (`esp32s3`, `wt32-eth01`). `state.h` is the single shared `SRTState` struct — all subsystems mutate it directly. Coordinate transforms are in `coordinates.cpp` (Julian date, GMST, precession J2000↔date, RA/Dec↔Alt/Az, galactic↔equatorial, sun/moon ephemeris). The web UI is a single embedded HTML string in `index_html.h` — heavy use of inline JS and `fetch()` against the various web_server.cpp endpoints. `/ping` and `/network` are minimal diagnostics kept ahead of the full UI handler. In `/status`, `alt`/`az` are the Due's **drive** position (the scheduler's slew check and `sun_scan.py`'s record of where a source was found both need that frame) and `true_alt`/`true_az` are the sky position they correspond to; RA/Dec and galactic l/b are computed from the latter. Goto/track endpoints reject targets below `settings.horizonAlt` before mutating state.

**Operator page** (`receiver_scheduler/web/`): plain static files — `index.html`, `app.css`, and twelve scripts under `js/` — served by `index` and `page_asset` in `h1_web_scheduler.py`, the same pattern as `/simulator/`. Until 2026-08-25 the whole page was a 3184-line Python string inside that module, 41% of the file. Do not put it back: a Python string applies **Python's** escapes to the JavaScript before the browser sees it, which killed every handler on the page twice in two days — a stray apostrophe from `\'` on 08-24, and a `\n` written into an `alert()` on 08-25 that broke the string across lines. Both times the server went on answering in a millisecond. Editing the page now needs only a browser refresh, not a scheduler restart, because the files are read per request.

The scripts load as **ordered classic scripts, not ES modules**, and share one global scope. That is deliberate: there are 46 cross-file references and they are circular (`shared` starts every tab's polling from `switchTab`, and every tab calls back into `shared`; `schedule` and `shared` reference each other 17 times). ES modules tolerate cycles but fail at runtime on particular paths, and with no node on this host the JavaScript cannot be executed to prove otherwise. Order matters in exactly two places: `state.js` first, because `let`/`const` are not hoisted and an earlier file would meet them in the temporal dead zone; and `boot.js` last, being the five statements that execute on load. Everything else is hoisted function declarations. Moving to real ES modules is still worthwhile *per tab*, once there is a way to run the JavaScript — a headless browser check, or node installed.

`test_page_structure.py` guards all of this through `page_sources.fetch_page`, which asks Flask for the page and follows whatever scripts it names, so the same tests run whatever the arrangement. Four invariants: every `getElementById` has a matching id (markup **or** script-generated — the RF countdown div exists only in `rf.js`); every inline `on*=` handler names something callable, which is what an ES-module conversion would break silently at click time; every `fetch` path is a real Flask route; and nothing in `test_data/page_baseline.json` has been lost. Regenerate that baseline with `python test_page_structure.py --bless`, deliberately — never to make a test pass.

**Why the routes are not blueprints**: 34% of the 56 route handlers touch module-level state and 24 places use `global` to rebind it. `global` does not rebind across modules, so splitting routes into blueprints requires converting all of that to a shared state object first — it is not independent of the state refactor, and was mis-scoped as such on 2026-08-25. Do the state work first or leave the routing alone.

**Receiver scheduler runtime** (`receiver_scheduler/h1_web_scheduler.py`): Flask scheduler defaults to controller `http://192.168.50.120` (the private link above). Receiver processes always use `receiver_python_path` (radioconda by default), and the scheduler re-execs under that interpreter unless already there. **The scheduler always runs headless** — the observatory is normally worked over ssh, so nothing in the observing path may need a display. `start_observation` runs the receiver with **`--headless`**, which takes a Qt-free path: no `QApplication`, no widgets, no event loop, and PyQt is not even imported (`b210_h1_receiver.py` reads the flag out of `argv` before the import, because importing it maps the Qt5 libraries into every observation and cannot be undone later). `GNURadioFlowgraph` never had any Qt in it and is shared; `init_hdf5`/`append_spectrum` are module-level so the window and `HeadlessRecorder` write identical files. Measured: 3.8 MB RSS against 210 MB for the GUI, and no Qt mappings at all. Before this, an observation launched anywhere without an X server died at startup with "could not connect to display". A manual receiver boot (`/api/receiver/start`) is the **one** deliberately graphical path — it is for warm-up/testing at the console and will fail over ssh, which is correct. Scheduled observations stop it before acquiring the SDR, and `/api/receiver/status` reports whether the active process is manual or observation-owned. A receiver that exits on its own is reaped by `scheduler_thread` for *any* observation, not only one whose schedule slot is still due, and its own log file (`<output>.receiver.log`) has its tail copied into `scheduler.log` on an unexpected exit. A scheduled observation always wins: it cancels a running Sun scan/calibration day and waits (`SUN_SCAN_PREEMPT_TIMEOUT`) for the SDR before starting. `start_observation` claims the start briefly under `process_lock`, then does pointing/slew-wait unlocked and abortable via `start_abort` — do not reintroduce blocking work under that lock. Failed or short-lived starts back off after `MAX_START_FAILURES` per schedule slot. CORS is restricted to the configured controller origins — the ESP32 page's scheduler buttons only work if `srt_controller_url`/fallbacks match its origin. `/api/config` accepts only keys present in `_DEFAULT_CONFIG`, and observation filenames are contained inside the data folder.

**One owner of the SDR and the mount** (`hardware_in_use()` in `h1_web_scheduler.py`): six things can claim the hardware — a scheduled observation, a Sun scan, a calibration day, a horizon scan, an RF calibration, and the hand-started receiver GUI. Each start path used to carry its own list of what it refused to run alongside, and the lists had drifted: on 2026-08-25 a Sun scan would start during a horizon scan, a calibration day during either, and the horizon scan and RF calibration would both start on top of a receiver booted by hand. Every case was refused in the opposite order, which is why none had surfaced — starting things in the habitual sequence works. `test_exclusion.py` now tests the matrix **as a matrix**, every pair both ways, plus that each can still start when nothing holds the hardware (a guard that refuses everything would otherwise pass).

Two things about that are worth keeping. A scheduled observation is deliberately *outside* the check, because it preempts rather than defers — it is the only claimant whose slot cannot be re-run later. And the first version enumerated the **subsystems** rather than the **claimants**, which is how the manual receiver was missed: it has no state dict and no tab. Add anything that can hold the radio to that one function, not to four start paths.

Read them with `gh issue view N --comments`; each carries the finding, `file:line` references, a "Suggested approach" section, and its verification steps. They supersede the former `docs/code_review_2026-08-05.md` and `docs/POINTING_CALIBRATION_IMPROVEMENTS.md`, both removed (the review remains in git history).

Issues labelled **`needs-hardware`** (#1-#4, #7, #9) cannot be verified on a dev host — they need a bench ESP32, `tools/due_emulator.py`, or the mount, and are compile-check-only elsewhere. #5, #6 and the scheduler half of #8 are fully testable under pytest. **Scheduler/receiver tests**: run with the radioconda Python: `cd receiver_scheduler && python -m pytest` (379 tests as of 2026-08-25). `TestFlaskAPI::test_post_config` fails on the observatory host because it makes a real HTTP call and reaches the live controller, which then syncs the observer location back over the value the test just set — a test-isolation bug, unrelated to whatever you are changing; check it against a clean tree before chasing it. The receiver GUI runs without hardware via `--sdr demo`; two instances no longer collide over one filename, since each gets its own timestamp (they still contend for the SDR).

**Where recordings go, and what they are called** (`receiver_scheduler/observation_files.py`, shared by the scheduler and the receiver — the scheduler cannot import the receiver back, which pulls in GNU Radio at module scope). Every recording lands in `data/observations/`, named `YYYYMMDD_HHMMSS_<mode>.h5` and nothing more. Two rules, and both were arrived at by watching them broken:

- **The name carries only what the file cannot.** The old name held the target and the calibrator flag, both of which are already attributes (`obs_name`, `calibrator`, from `H1_OBS_METADATA`) — a second copy free to disagree with the first after any rename or any edit to the schedule entry. What is left is the time, which the name cannot be wrong about, and the mode.
- **`track` / `drift` describes the mount, not the entry.** `track` means it followed the sky; `drift` means it was parked and the sky moved through the beam. That decides whether successive rows of a spectrogram are the same piece of sky, so it earns its place. Note that an **`altaz` entry is a drift scan** — the scheduler sends it to `/direct` with tracking off — and `TRACKING_COORD_SYSTEMS` is a description of what `srt_point_telescope()` actually does. If the two ever disagree, the filename is the one that is wrong. The same word is stored as the `observation_mode` attribute.

A recording made at the console is `manual`: nobody commanded the mount, so claiming either mode would be inventing one. `data/` itself stays the general working folder (plots, horizon partials, gain fits, bandpass templates) — on 2026-08-25 it held 248 files of which 11 were observations, which is what prompted the split. The receiver's `OUTPUT_FILE` default is now resolved against its own directory rather than the working directory; as a bare `"h1_data.h5"` it had scattered 22 files across the repository root, because the scheduler launches it with `cwd=repo_root`. `H1_OUTPUT_FILE` still overrides everything. A mid-run roll (frequency axis or FFT width changed under the receiver) gets a fresh timestamped name too, with the reason recorded as the `segment`/`segment_reason` attributes instead of spelled out in the filename.

**Recordings can be read while they are being written** (issue #20, done 2026-08-26): `init_hdf5` opens with `libver='latest'` and switches the file to SWMR mode once every dataset and attribute exists. The constraints — nothing created after that point, anything extended chunked — were already met by the layout, which is why the change was two lines: every extensible dataset has a `maxshape`, every attribute (tuning, scheduler metadata, embedded calibration) is written before the first spectrum, and a geometry change rolls to a new file. The one attribute that used to be written afterwards, the segment number of a rolled file, now goes in through `init_hdf5` arguments. Readers go through `observation_plot.open_readonly`: a plain open first, and on the HDF5 lock the SWMR open, seeing the file as of the writer's last flush (per record). A recording made before this date still refuses while open, honestly, since it cannot be read consistently. The cost is the HDF5 1.10 on-disk format — fine for h5py, current MATLAB and the notebook (`swmr=True` to open a live file there). The Observe tab's **View live recording** selects the file being written and re-plots it every 30 s until the run ends; the catalogue marks it "(recording — live)"; Fit model runs on what has arrived so far and says `live`, and such a fit is never applicable as the calibration. The `.live.jsonl` sidecar stays for the live *plot*: one number per record from a text file is cheaper to poll than reopening an HDF5, and immune to a torn read.

**Recorded units are in the dataset name.** `spectra_kelvin` means the bandpass template and gain in force were applied at write time; `spectra_linear` means they did not apply to that tuning and the data are raw counts. `spectra_units` says the same thing, but the *name* is the guard: asking for the wrong one raises `KeyError` rather than silently returning the other scale. Writing in kelvin is safe only because it is exactly reversible — `bandpass_correction`, `applied_gain_counts_per_k` and `applied_t_sys_k` all travel in the file, and `observation_plot.read_observation` reverses it so `reduce_for_fit` is handed counts. That reversal is not a wasted round trip: fitting a gain from spectra a gain has already been applied to is circular, and would return unity and a system temperature of zero *while looking like a perfect calibration*.

**Sun scan calibration** (`receiver_scheduler/sun_scan.py`): scan offsets are sky/cross-elevation offsets. Commands recompute the Sun position before each point, expand mount azimuth by `cos(alt)`, clamp to the usable azimuth range, and save both mount azimuth correction (`az_error_deg`) and fitted sky correction (`az_error_sky_deg`) against the mid-scan Sun position.

**Obstructed horizon**: the calibration day does not scan the Sun while it is behind an obstruction, and `fit_pointing_model(obstruction_sectors=...)` leaves any scan already on file from behind one out of the fit, reporting the count as `n_obstructed`. The reason is that trees are a **source** at 1420 MHz, not a screen: foliage at ~290 K entering the lower rows of the raster puts a ramp under the Sun and drags the single Gaussian's centroid down into it, so the scan is wrong rather than merely noisy and its stated centroid uncertainty gives no warning. On 2026-08-20 the first four scans (Sun 18–29°, az 94–112°) fitted 0.5–1.2° low in altitude while the evening scans at the *same altitudes* in the west were clean — that east/west asymmetry, not the low elevation, is what identifies it. Like `true_lat`/`true_lon`, the sectors are passed into the fit by the caller so the fit stays a pure function of the data it is handed.

The sectors themselves are **derived from the measured horizon profile** (`horizon_obstruction_sectors`, `sun_raster_obstruction_sectors` in `h1_web_scheduler.py`). The hand-entered `obstruction_sectors` config key was **retired on 2026-08-25** — it was the single blanket entry `[[45, 120, 30]]` read off one calibration day, standing in for a measurement nobody had yet; the profile knows each azimuth separately, and the eastern floors it replaced range from 15° to 30°. Consumers still take `[az_min, az_max, min_alt]` triples, so only the source changed.

Before driving a raster — the calibration day and `/api/sunscan/start` — **every raster point is checked**, not the Sun's position with an allowance (`sun_scan.raster_obstruction`, built on the same `_sun_offset_to_command` the scan itself uses, so the points checked are the points visited, cos(alt) azimuth expansion included). The sectors there carry a **beam-only** margin: the raster's reach is enumerated, not allowed for, and adding both would count the extent twice. The whole scan is rejected if any single point is obstructed — a contaminated point does not merely lose itself, it puts a ramp under the single Gaussian and pulls the centroid, so there is nothing to salvage by dropping it. This is the one place the horizon **refuses** rather than warns; untick "respect local horizon" to force one. The centre-only test is not equivalent even in principle, because the raster spans azimuth and the horizon varies with it: on the 08-24 profile a Sun at alt 52 az 5 is itself clear while the raster's bottom row lands 1.2° short.

`sun_raster_obstruction_sectors` (beam + `(n-1)/2 × spacing`, 8.16° at the default 5×1.5° raster) survives for **one** caller: excluding already-recorded scans from the fit, where records store `sun_alt_deg`/`sun_az_deg` but not the raster geometry, so it cannot be reconstructed. Do not use it for a raster about to be driven.

With **no profile measured nothing is excluded** — there is no fallback list, because inventing a default would claim knowledge of a skyline nobody has surveyed. Run a horizon scan before trusting a calibration on a new site.

**Respecting the measured horizon** (`respect_local_horizon`, on by default): a tickbox on the Observe, RF calibration and Sun scan tabs and on every scheduled observation. It is **advisory almost everywhere** — a profile can be months old and stopping an observation on the word of a stale measurement is worse than knowingly taking a contaminated one. Clearance asks for the **full** beamwidth above the measured floor, not the half: foliage at 1420 MHz is a ~290 K source, so a beam clipping it gains signal rather than losing it. The check reads `true_alt`/`true_az` from `/status` after the slew, which is the frame the horizon was measured in, so one code path serves alt/az, RA/Dec, galactic and named objects with no second ephemeris.

Two exceptions where it acts rather than warns. **Scheduled observations are trimmed**: the window is rewritten to the longest stretch with the target clear, and one with no clear stretch is marked and skipped. Longest clear *run*, not merely clear at both ends — a circumpolar target can be clear at start and finish and pass behind a 45° tower between. The trim is idempotent, which is what makes rewriting the stored entry safe. Satellites, calibration days and horizon scans are exempt; the horizon scan necessarily so, or it could never re-measure where the sky was last found blocked. **Sun rasters are refused**: every raster point is checked before driving any of it, using the same `_sun_offset_to_command` the scan uses so the points checked are the points visited. A contaminated point does not merely lose itself — it puts a ramp under the single Gaussian and pulls the centroid — so rejection is whole-raster. Untick to force one.

**Horizon scan** (`receiver_scheduler/horizon_scan.py`): maps the obstructed horizon radiometrically — trees, roofline and the two dome towers are ~290 K sources at 1420 MHz, so lowering the beam through them is a large step in total power, of order the system temperature rather than a marginal excess. Not everything is: a **metal-clad building** has very low emissivity, reflects cold sky rather than radiating at ambient, and showed only 2.3% of sky where the treeline gives 59%. That is still a ~25 sigma detection against radiometric noise of 0.09%, so it is detectable — but anything judged by a fixed percentage rather than by significance will miss it and report a building as open sky, which is the unsafe direction. `horizon_floor()` takes the **worse** of the two bracketing azimuths, since a narrow obstruction is likelier to be missed than double-counted, and `--sdr demo` runs the whole thing against a synthetic horizon with no hardware, flagged in the UI so it cannot be mistaken for the real one.

An earlier **per-azimuth cut scan** — sweeping altitude at fixed azimuth, fitting a beam-convolved erfc, with a tracking window, an envelope fallback and a retry ladder — was removed on 2026-08-21 after three unusable runs. It is in the history if the fitted geometric edge is ever wanted again, but do not resurrect it casually: it is what lost the encoder counts, and its tracking window could ratchet, where one bad cut moved the next window above the horizon and poisoned every azimuth after it.

**Horizon strip scan** (`horizon_strip_scan()`) is the pattern to use for a whole-sky measurement; the per-azimuth cut scan above is now a fine-resolution tool for the few azimuths that warrant one. Strips sweep **azimuth at constant altitude**, 5° in both axes, climbing from 5°. The reason is mechanical: the cut scan moved the **altitude** axis thousands of times and repeatedly into its lower limit, and on 2026-08-21 that axis lost encoder counts mid-sweep (see below). Strips move altitude once per strip. Three defences come with it — the mount **re-homes every second strip**, bounding any count loss to one strip; a **sky reference** at a fixed high position is measured at the start and after each homing, as a running health check; and an azimuth found clear is **dropped from every higher strip**, because the horizon is monotonic, so the work peels away (70 azimuths → 24 → 7 → none) and the whole sky costs ~225 points, about 26 minutes.

The clearing threshold is the subtle part, and both obvious choices are wrong. It cannot be judged against the **zenith**, because clear sky low down is genuinely warmer through airmass and spillover — measured 0.0114 at alt 8° against 0.0089 at the zenith — so a zenith threshold calls every low azimuth blocked. It cannot be judged against the **strip's own distribution** either, because by the top strip everything still pending is blocked and a percentile of it would clear the tower along with the sky. So three azimuths that cleared on the first strip are re-measured at *every* altitude and are the reference, at the right airmass. They are recorded in the profile as `control_azimuths`: if one of them was obstructed after all, every threshold above the first strip was set too high. The cost of 5° altitude steps is that there are ~2 samples across a 5.8° beam, far too few to fit an edge — so a strip scan reports **the lowest altitude at which an azimuth reads clear**, not a fitted geometric edge.

**Lost encoder counts, 2026-08-21** — the failure mode to recognise, because nothing in software reported it. Symptoms in order: the sky level stayed rock steady while the *ground* signal faded; `p_ground` fell monotonically with azimuth across a sweep (time and azimuth are confounded when scanning in order, so this reads as a property of direction); an azimuth measured three hours earlier disagreed with itself; and finally the tower at az 5, a fixed structure, dropped from 0.0065 excess to 0.0009. The dish was physically nowhere near where the controller believed, having travelled past 90° altitude, which the drives permit. **Reference values for diagnosing this** (2.4 MHz, 0.5 s, gain 40): sky 0.0088–0.0092 at any azimuth; the tower at az 5 alt 5 reads 0.0153, an excess of **0.0054–0.0065**; healthy sky repeatability is 1 part in 10⁴ and pointing repeatability better than one encoder pulse. An excess near 0.0009 means the pointing is wrong, not the receiver — the *baseline staying constant while the antenna contribution collapses* is what separates a pointing fault from a signal-path fault, since a lossy cable would drag both. Any scan that visits positions monotonically should revisit a fixed reference periodically, or it cannot tell a property of direction from a drift in time.

**The horizon archive** (`astro_simulator/horizon_store.py`): the horizon is seasonal — trees leaf out through the summer and are cut back between seasons — so scans are **kept by date and never overwritten**, under `receiver_scheduler/horizon_profiles/horizon_<UTC stamp>.json`, with `active.json` naming the one in force. The stamp comes from the scan's `started_utc`, so the dozen partial saves of one night collapse onto one file rather than littering the list.

A finished scan is **archived but not adopted**. Choosing is a separate act (`set_active`, or the Horizon tab's dropdown), and deliberately so: a pruning genuinely opens the sky, so a fresh scan reads lower than the one before it, and a scan that took effect on its own would drop the horizon with nobody having agreed the new measurement is the better record — destroying the old one in the same stroke, which is what the single overwritten file used to do. The one exception is the first scan on a fresh installation. `set_active` also rewrites the legacy `horizon_profile.json` as a mirror, so every existing reader of that path follows the choice without knowing the archive exists; with nothing chosen, `load_active()` falls back to the most recent complete non-demo scan, but a fallback is not a choice and `active_name()` still reports `None`.

The store is **stdlib-only and lives on the simulator side** for the same reason `instrument.py` does — that is the layer everything may depend on, and the simulator draws the measured horizon without importing the scheduler. `profile_floors` / `horizon_floor` / `is_obstructed` moved there and are re-exported from `horizon_scan` so existing callers are unaffected. Note the import contract: `horizon_store` is only importable after `observatory` has put `astro_simulator/` on the path.

`horizon_castellation()` samples `horizon_floor` rather than joining the measured points, so the line drawn on the simulator (orange, above the white alt=0 great circle, toggled by the "Horizon: measured" button) **is** the rule that decides whether a target is blocked. It is stepped, not smoothed, because the rule between two samples really is "the worse of the two" — a smooth curve would claim a precision the 10° sampling does not have, and would claim it on the optimistic side.

A horizon scan is also a **schedulable observation type** (`coord_system: "horizon"`, alongside `"calibration"`), so the twice-yearly measurement can be booked for a dark night rather than needing someone awake — it takes ~2 hours. It runs as a thread that owns the SDR and the mount, is tracked as the running observation, stows on `end_action`, and is preempted by any real observation. Like the calibration day, a scan that *finishes* inside its slot still counts as occupying it, or the scheduler would restart it from the top; unlike the calibration day, a partial profile is never saved, so stopping simply abandons the run.

**Velocity frame**: recorded spectra are plotted on an **LSR** axis whenever the direction and epoch can be worked out (`lsr_offset_km_s` in `observation_plot.py`). The recorded axis is the raw Doppler shift and carries the Earth's orbit and rotation plus the Sun's motion — up to ~30 km/s, varying with direction and date — so a topocentric axis cannot be compared with published data, with the simulator, or with the same source six months later. The conversion is `astro_simulator.frame_offset`, already proven in the other direction by `rf_calibration.simulated_spectrum`; it returns what to **add** to an LSR axis to reach the observed frame, so recovering LSR **subtracts** it. Evaluated at the observation's own epoch and mid-point, never "now" — the barycentric term moves 1.95 km/s in a week. Applied for display only, so recordings stay raw and re-reduce correctly. Where the direction is unknown the axis stays topocentric and says so.

Validated at the galactic anticentre, where rotation contributes nothing along the line of sight: the 2026-08-25 l=184 b=0 observation peaked at −11.17 km/s topocentric and lands at **+3.75 km/s** corrected, against HI4PI's +3.97 — **0.22 km/s**, from 15 km/s before.

**The B210 clock is stable**, and the note that said otherwise was wrong. `fit_gain_with_shift` recorded "the clock really moved by 3.7 ppm in an hour and a half", from three fields agreeing at −5.9 to −6.9 ppm against −2.67 an hour later. Re-fitting all eight archived calibrations against a settled bandpass shows that scatter tracks **line strength, not time**: correlations of 0.999 on the plane give −2.63 and −2.09 ppm, while 0.41–0.93 on weak high-latitude fields give −6.6 to +18.4. A shift with no line to hold it slides onto whatever is nearby and reports a confident number. Constrained fits only: **−2.36 ± 0.27 ppm over 18 hours**, ±0.08 km/s, well inside the ±2 ppm the part is specified at. So the fitted shift **is** carried between observations, but only from a fit whose correlation says a line held it (`trustworthy_velocity_shift`, ≥0.99). The wider lesson: a quantity fitted alongside others takes up their slack, and these were read as a property of the clock when they were a property of the fit.

**Slew polling**: `_slew_to` polls `/status` every `_SLEW_POLL_INTERVAL_S` (0.2 s), not the 1 s it used to. Measured 2026-08-21: axes run at 3.9°/s in altitude and 2.9°/s in azimuth, a 1° move costs ~1.5 s end to end of which only 0.3 s is motion, so the old interval was most of the cost of a raster. Do **not** poll flat out — with no gap at all the ESP32 resets the connection after a few requests; 50 ms sustained 14 Hz in testing. Deliberately slower than it can stand, though: the average wait is half the interval, so 200 ms costs 0.1 s against 0.05 s at 100 ms — a twentieth of a second per point — for half the request rate on a controller with known cross-task locking weaknesses (issue #1). Either way 0.4 s of the old 0.45 s is recovered. More requests per slew means transient failures are expected, so they are tolerated up to `_SLEW_STATUS_FAILURES_ALLOWED`, and `_srt_api` retries transport errors for every caller — safe because every controller endpoint is idempotent (`/direct` and `/go-home` command absolute positions). Structural wobble was measured (camera, sub-pixel) at ≲0.2–0.3° after a slew and was judged too small to need a settle pause; the encoders see nothing at all, since the flex is beyond them.

**Solar flux monitor**: a "Solar track" mode on the Observe tab — an ordinary tracked observation (`coord_system: "object"`, `object_name: "sun"`), so it needs no new subsystem and records full spectra as usual. Live flux is read from `<output>.live.jsonl`, one line per record written by `_append_live_summary` in `b210_h1_receiver.py`, because the HDF5 cannot be opened while it is being written (no SWMR; live *spectrum* display is issue #15). The value is the **median** across the band — it ignores the LO artefact and narrow RFI without having to find them, and for a broadband source it is the continuum level. Converted with the stored gain, minus T_sys, then the antenna theorem with the measured beam: `A_e = λ²/Ω_A` gives **4.84 m²** against a physical 7.07, an aperture efficiency of 0.68 that is an output of the measurement rather than an input. The plot bins the **whole** run rather than showing its tail and polls at the record cadence (clamped 2–30 s). It **comes down when the run ends** (2026-08-26): the recording can be plotted directly now that it is readable, and that plot is the better picture of the same data, so the page switches the viewer to the just-finished file and draws it in the live trace's place. `/api/observe/live` still answers for a finished run (`finished: true`); only the page stops showing it.

**Drift scans park on the drive grid** (`receiver_scheduler/drift_park.py`, 2026-08-26): the Due rounds every target to the nearest encoder pulse (`executeDrive`, 0.5°), after the controller has applied refraction and the model, so "park where the source is at T" actually parks up to 0.25° per axis away — a crossing up to ~2 min off T plus a cross-drift miss of up to 0.35°, which is what the first comparisons of Cas A, Crab and Sun scans against the planned T were partly seeing. Now `srt_point_telescope` reads the controller's terms from `/pointing`, reproduces `trueToDrive` in Python (`drift_park.true_to_drive`, validated in `test_drift_park.py` against (drive, true) pairs the controller itself reported), samples the source's track ±4 min around T, and parks on the grid point the track passes **closest** to, sending `/direct` the *true* position of that point so the controller's own rounding has nothing to do. The crossing time is then exact and known to the second, the miss is cross-drift only, and both are recorded (`drift_crossing_time`, `drift_crossing_offset_deg`, `drift_drive_alt/az`) — the live plot marks the recorded crossing rather than the slot mid-point. After the slew, `confirm_drift_parking` recomputes the crossing model-free from the `true_alt/true_az` the controller reports for where it parked, and warns if the drive position is not the planned one, so the file never depends on the Python copy agreeing with the firmware. Two things learned writing it: the controller's three-pass inverse leaves 0.1° of azimuth at alt 85 where the `sec(alt)` term is clamped (`drive_to_true` here iterates to convergence, because the *forward* of what is sent must land on the grid point); and a track along a grid line passes several points equally well, so ties within `TIE_DEG` go to the one nearest T. With `/pointing` unreadable it falls back to the old behaviour and says so.

**Home the mount first** (`home_first` on a schedule entry, tickbox on the schedule form, 2026-08-26): `start_observation` runs the Due's physical homing through `srt_home_with_report` before pointing, and a homing that fails or faults aborts the observation. While it runs, the controller's `/serial/log` is polled every half second, because that ring buffer is **30 lines — fifteen seconds of status** — and the reading that matters is gone by the time the sequence ends. The Due reports its position all the way into the stops, so the last `Alt:… Az:…` line before each `Homing: <axis> limit reached` is the counter at the stall (`_homing_counters`): on the **first approach** that is the count error accumulated since the previous homing (the stop is the true zero), on the **re-approach** it is the repeatability of the stop. Both go in the log, and the first-approach values are written to the recording as `homing_count_error_alt_deg`/`_az_deg` beside `homed_first`. This is the measurement that was lost on 2026-08-26 when a homing was run without the capture; issue #24 is the Due printing it itself. It costs about three minutes of the slot, so it is off by default.

**Live drift-scan plot**: drift scans get the same live trace (`live_plot_kind()` decides — `'solar'`, `'drift'`, or `None`; an `altaz` entry is `'drift'`, the same rule as the filename). Three deliberate choices. The **time axis is the observation's own window**, fixed from the start, with the beam-crossing time marked at the mid-point — an axis scaled to the data can never show how far through a transit is, and "the source peaked in the middle of the plot" is true of every autoscaled plot ever drawn. `last_observation` carries the *planned* end (`ends_at`) beside the actual one so a scan stopped early keeps showing the stretch it never reached. The y-axis is **antenna temperature**, not SFU (a solar convention). And a **tracked spectrum gets no live plot at all**: its band power is meant to be flat, so an autoscaled trace of it is a magnified picture of the noise. The plotted number is the band **median of the bandpass-corrected spectrum over the channels the template covers** — the raw full-band median is ~8% low against the scale the gain was fitted on, which was invisible on the Sun and put a blank-sky drift scan at a steady −24 K. Whether the calibration applies is decided *before* the records branch (it is a property of the tuning, not the data), so the axes drawn while waiting for the first record are not labelled "uncalibrated". The warm-up cut is **proportionate**: a record is dropped only when the 5 s settle covers more than a tenth of it — the flat 5 s rule discarded an entire 60 s record and doubled the wait for the first point. First point lands at slew + one integration + poll; for faster feedback shorten the integration, the plot bins it back down anyway. Two hard-won test patterns live in `test_live_plot.py`: every Flask view may only require arguments its URL rule supplies (a helper defined between `@app.route` and its function silently *becomes* the view — every request 500s and no test notices), and the endpoint tests run against real sidecar files.

**Fit model on the Observe tab** (`/api/observe/fit`): for a tracked spectrum, the RF tab's per-channel gain fit (`rf_calibration.calibrate_observation`) on the chosen recording — a proposal, drawn with `plot_gain_check`, compared with the calibration in force, applied only by a separate confirm. For a **drift scan it is a different fit altogether** (`drift_fit.py`): total power against the simulator's predicted drift curve, `counts(t) = G·(T_sys + T_model(t))`, two parameters by least squares, T_model being the band-mean sky (H I cube + diffuse continuum + the bright sources, through the measured beam) at the fixed alt/az as it drifts. It needs **no bandpass template** — the bandpass shape is the same constant on every record and lives inside G — so it works at any tuning, which is what the per-channel fit rightly refuses. The two gains are different numbers (this one carries the band-mean of the bandpass and belongs to its band), so a total-power fit is drawn and reported, never applied as the per-channel calibration; `applicable: false`. First run on the 2026-08-25/26 Cas A scan at 1419 MHz: correlation 0.86 over five hours, the Cygnus-region hump and the plane matching, and it dissolved that morning's "2× too bright" puzzle — the model's 6 K span is Cas A *plus the plane's continuum along the track*. Then the operator asked whether the convolution was right, and it is — Cas A comes out 2.90 K through a 5.164° beam at η = 1, exactly by hand — but the check exposed a limit of the fit: the "constant" bandpass factor is only constant for a flat sky. The band mean sums channels with different gains, the H I line dominated the model's structure on the plane, and line channels were 12% hotter than continuum ones, so the fitted G was a mixture and Cas A on that scale read 1.7–2.4× depending on which channels anchored it. **Anchoring the gain on the H I line alone** — its slope against the model, 1.43×10⁻⁵ counts/K — agrees with the per-channel calibration to 5%, which is what the 1.4 MHz LO shift predicts; that validates the H I cube through the beam. On that scale Cas A is **1.46× the model (4.1 K vs 2.8) with a 29-minute crossing against 40 predicted, centred +5 min** after the end-of-record stamp convention is removed. A narrower beam predicts both: (5.16/3.8)² = 1.8 in amplitude and 0.74 in width. But 4 K from 1650 Jy needs A_e ≈ 6 m² — an aperture efficiency near 0.85 on a 3 m mesh dish, which is hard to believe — so either Cas A is brighter than the secular-fade estimate or the point-source response is genuinely higher at the zenith (alt 87°) than the Sun scans see at 20–50°, where gravity shapes a mesh dish differently. **Unresolved.** The test is elevation: Tau A transits at alt 56° (Sun-scan territory) and Cyg A at 75°; drift scans of both at the standard tuning, widths and amplitudes compared. The diffuse continuum map correlates only 0.65 with the continuum channels over five hours of thermal drift and says little either way. One candidate was checked and eliminated the same day: the survey's handling of the source. Cas A is blanked in the Stockert map and the compression inpaints the hole with a flat annulus median, and the 0.65° PSF subtraction leaves a **residual halo around all three strong sources** (issue #23; Tau A: 3.1 K at the centre falling to 0.75 K only beyond ~1.5°). The model therefore double-counts ~0.5 K beam-averaged at the Cas A crossing — but that pushes the model *up*, so it makes the measured excess slightly larger, not smaller. It is a real map defect, and it is not this puzzle.

**Gain calibration goes stale with temperature**: the fitted gain fell 2.1% (and T_sys 4.3 K) between 12:25 and 20:16 on 2026-08-25 — the B210 cools after sunset — which on a 350 K system reads as a −17 K offset on an absolutely-calibrated drift scan. ~0.3%/h through the evening transition. Calibrate adjacent to the observation that needs absolute temperatures; for a transit the offset is constant and harmless.

**Total-power instability, and the noise the simulator draws** (`GAIN_INSTABILITY` in `instrument.py`, 2.3×10⁻⁴): the practical radiometer equation is `ΔT/T_sys = √(1/(Δν·τ) + (ΔG/G)²)` — the second term is why Dicke switching exists, and it is missing from σ = T_sys/√(Δν·τ) tooling because line work is per-channel (thermal wins) or switched (common mode cancels). An unswitched band-integrated drift scan is the one regime where neither escape applies: at Δν·τ ≈ 2×10⁸ the measured white common-mode wobble of 2.3×10⁻⁴ (0.079 K per 60 s record, **second differences** of the band mean over a settled 99-record run, stationary across halves) sits 3.4× above the band-mean thermal floor, while the *per-channel* scatter is simultaneously thermal to 6% — compatible because thermal divides by √N_chan on the integral and common mode does not. Receiver gain and atmospheric emission are indistinguishable without a switched reference; the constant is their sum. Both simulators add it in quadrature to **drift-scan samples only** — in a spectrum it is a flat ±0.08 K common-mode baseline offset, 7× under per-channel thermal, averaging down across records and removed exactly by any baseline handling, so modelling it there would add noise the science cannot see. It ships to the web build as `meta.json defaults.gain_sigma` (regenerate with `make_web_data.py --meta`; the staleness test checks it). Practical corollaries: the Allan minimum for band power is ~5 s at 3.7 MHz — beyond that, more samples beat longer samples — and the upgrade path if band-integrated continuum ever becomes a science goal is Dicke-style switching of the existing `Cal ON/OFF` noise diode. **It was first installed as 1.1×10⁻³**, from four first-differences on a freshly started receiver on the wrong run's sidecar: warm-up transient + real sky drift + instability read as one number. Second differences on a settled run are the measurement; anything less repeats the mistake.

Measured 2026-08-25: **112 SFU** against RSTN 1415 MHz that day of 88 (Learmonth) and 108 (San Vito) — the two stations disagree by 10–20 SFU every day, so this is agreement to within the reference network's own spread. That is the first end-to-end check of bandpass, gain, T_sys, beam and the antenna theorem against an external standard.

**Tracking scallops as expected, and does not sawtooth.** The drive quantises at one encoder pulse, 0.5°, so on a 5.164° beam the error sawtooths ±0.25° and the gain follows a parabola. Predicted fundamental **0.263%**; measured **0.429% ± 0.121%** at the independently predicted 4.3-minute altitude-step period (3.6σ). A sawtooth — error 0→0.5°, meaning no look-ahead — predicts **0.859%** and is excluded at 3.6σ. So `round()` really does perform the lead (issue #7). The residual is consistent with a ~0.10° bias but only at 1.4σ; resolving that needs ~4× the integration. Note the periodogram measures a *sinusoid*, so compare against 0.263% and not the 0.65% peak loss.

**Tests and the log**: `receiver_scheduler/conftest.py` detaches the `scheduler`, `sun_scan` and `horizon_scan` loggers from their file handler for the test session. Importing `h1_web_scheduler` attaches them, so without it any test running a demo scan writes "Az 40 deg: edge ..." into the live `scheduler.log`, interleaved with real telescope operations. That cost time twice on 2026-08-21 — once chasing a phantom "scheduled observation preempts" during a real run, once when a progress monitor read the tests' demo azimuths as measurements. The log is the operational record of what the telescope did.

`conftest.py` also redirects `LAST_OBSERVATION_FILE`, for the same reason: several tests run the real `stop_observation`, which writes that pointer, so a test run left the Observe tab offering a plot of "StopMe" from `/tmp` while the observatory's actual last run sat unreferenced. Session-scoped and autouse rather than left to each test, because the tests that write it do so *through* `stop_observation` and it is not visible from reading one that it needs isolating.

**No test may open the radio.** `test_the_mount_is_homed_between_strips` runs the non-demo path on purpose (demo mode skips homing) and stubbed the measurement but not the B210 session, so it opened the real device — passing whenever the SDR happened to be free, and failing on 2026-08-25 in the middle of an observation. Failing was the good outcome: a unit test that can take the radio from a running observation is a worse bug than anything it was written to catch. Stub `sun_scan._B210PowerMeter` as well as `_measure_at`.

## Conventions

- **Editor**: never use `cat`/`echo`/`sed` from Bash; use the dedicated Read/Edit/Write tools.
- **Forward slashes** in paths even on Windows (Bash tool runs in MSYS).
- **Status line format** (don't break it — the ESP32 parser is positional):
  `Alt:%.1f Az:%.1f Ialt:%.1fA Iaz:%.1fA Status:<state> [<fault>] -> Alt:%.1f Az:%.1f Cal:ON|OFF`
- **Don't use TodoWrite** for trivial in-conversation tasks. The user has it disabled in spirit and gentle reminders to use it should be ignored unless the task is multi-step and would actually benefit.
- **Don't run destructive git commands** (`reset --hard`, `push --force`, `--no-verify`) without explicit instruction. Commits are created on user request only.
